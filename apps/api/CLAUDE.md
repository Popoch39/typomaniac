# apps/api

API backend en [Elysia](https://elysiajs.com) sur le runtime Bun. Point d'entrée : `src/index.ts` (serveur sur le port 3000).

## Structure : best practices Elysia (obligatoire)

L'arborescence suit **impérativement** https://elysiajs.com/essential/best-practice.html : une feature = un module, avec controller, service et model.

```
src/
  app.ts  index.ts  env.ts  parse-env.ts  test-app.ts  app.test.ts
  lib/        transverse sans Elysia : api-prefix, clock, errors, logger
  plugins/    plugins Elysia transverses : request-id, logs, headers, rate-limit, error-handler, docs…
  database/   client, migrate, schema.ts (agrégat des tables pour drizzle-kit), auth-schema.ts (généré)
  modules/<feature>/
    index.ts      controller : factory `xModule(deps)` → `new Elysia({ name, seed })`, routes chaînées
    service.ts    logique métier, sans Elysia : fonctions, dépendances reçues en argument
    model.ts      schémas TypeBox groupés (`XModel = { … }`) + types dérivés (`typeof XModel.x.static`)
    index.test.ts tests du module (service.test.ts pour ceux du service)
    …             fichiers nommés quand le module en a besoin (store.ts, drizzle-store.ts, schema.ts…)
```

- Modules actuels : `auth` (instance Better Auth, macro `auth`), `me` (`/me`, avec le rang via `DuelStore.rankOf`, jamais le MMR ; `/me/pace`), `handle`, `user` (Users, recherche), `friend` (Friend requests, Friends), `duel`, `duel-history` (`/duels`, sur le `DuelStore`), `profile` (`/users/:handle/profile`, Stats sur le `DuelStore`), `leaderboard` (`/leaderboard`, le Classement sur le `DuelStore`), `activity` (`/activity`, sur le `DuelStore` et le `FriendStore`), `challenge` (sans route : ses messages passent par la socket du Duel).
- `app.ts` ne déclare pas de route métier (seulement `/health`) : il monte les plugins puis `.use()` chaque module. Chaque module fait `.use(authentication(…))` pour la macro (plugin nommé, dédupliqué).
- Le model est la source unique des types : pas d'interface parallèle aux schémas.
- Services : pas de classe statique ni de singleton ; les dépendances (`Users`, `DuelStore`, `Clock`…) passent en argument, injectées depuis `AppConfig` (tests sans `vi.mock`). Les classes à état (`DuelQueue`, `RunningDuel`) restent des classes.
- Les tables Drizzle d'une feature vivent dans son module (`modules/duel/schema.ts`) et sont réexportées par `database/schema.ts`.
- Une nouvelle feature = un nouveau dossier `modules/<feature>/`, jamais une route ajoutée dans `app.ts` ni un fichier à la racine de `src/`.

**Préfixe global `/api`** (`API_PREFIX`, `src/lib/api-prefix.ts`) : `createApp` est une `new Elysia({ prefix })`, donc toute route (y compris celles des plugins montés, comme la doc) vit sous `/api` ; hors préfixe, tout répond 404. Une route se déclare sans le préfixe (`.get("/health")`). Les hooks `onRequest` voient le pathname complet : ils comparent à `` `${API_PREFIX}/…` ``.

## Skill Elysia obligatoire

**Avant de créer, modifier ou relire un fichier qui utilise Elysia** (routes, plugins, handlers, schémas de validation, config du serveur), invoquer le skill `elysiajs`. Pas d'exception pour les petites modifications : l'API d'Elysia évolue vite et le skill porte les patterns à jour.

## Base de données

- Postgres + Drizzle, driver `drizzle-orm/bun-sql`. Schéma : `src/database/schema.ts`, client : `src/database/client.ts`.
- Postgres de dev : `docker compose up -d db` depuis la racine (port hôte **5434**, identifiants dans `.env` racine, voir `.env.example`).
- Config de l'api : `apps/api/.env` (voir `.env.example`), validée au démarrage par `src/parse-env.ts`. Toute nouvelle variable passe par ce schéma.
- Migrations : `db:generate` après chaque changement de schéma, fichiers SQL versionnés. Le serveur les applique au démarrage, avant `listen()`. Pas de `drizzle-kit push` ni `drizzle-kit migrate` (pas de driver Node installé).
- `drizzle-typebox` pour dériver les modèles Elysia du schéma. `@sinclair/typebox` est épinglé à la version qu'utilise Elysia : les monter ensemble.

## Image de prod

`apps/api/Dockerfile`, à builder depuis la racine : `docker build -f apps/api/Dockerfile -t typomaniac-api .`. Binaire compilé dans une image distroless, dossier `drizzle/` embarqué. Variables requises à l'exécution : `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` (et `PORT`, 3000 par défaut ; `CORS_ORIGIN`, origine du front, `http://localhost:5173` par défaut). En prod, poser `NODE_ENV=production` (logs JSON, HSTS) et trancher `TRUST_PROXY` selon l'hébergement.

## Logs et sécurité

Plugins dans `src/plugins/`, montés par `createApp` dans cet ordre : request-id, request-logger, security-headers, cors, api-docs, error-handler, body-limit, rate-limit, authentication (puis les modules me, handle, user, friend, duel-history, profile, leaderboard, activity, duel). L'error-handler doit rester avant les plugins qui rejettent des requêtes.

- **Logger** : pino, créé dans `src/index.ts` (`src/lib/logger.ts`) et injecté via `AppConfig.logger`. JSON sur stdout si `NODE_ENV=production`, sinon `pino-pretty` (transport worker, dev uniquement : il ne marche pas dans le binaire compilé). Niveau : `LOG_LEVEL`. Une ligne `request` par requête (méthode, path, status, durée, requestId). Dans un handler, utiliser `log` du contexte : il porte déjà le `requestId`.
- **Request ID** : `X-Request-Id` repris s'il est sûr (`[\w.-]{1,128}`), sinon UUID ; renvoyé dans la réponse. `requestIdOf(request)` pour le lire hors contexte (hooks d'erreur).
- **En-têtes de sécurité** : plugin maison façon helmet pour une API JSON (nosniff, CSP `default-src 'none'`, frame DENY, referrer, CORP/COOP). HSTS seulement en prod.
- **Rate limit** : plugin maison (`FixedWindowStore`, compteurs immuables : `elysia-rate-limit` v4 rejetait toutes les requêtes concurrentes proches de la limite). `RATE_LIMIT_MAX` requêtes par `RATE_LIMIT_WINDOW_MS` et par IP, 404 compris, `/api/health` exclu ; en-têtes `RateLimit-*` et `Retry-After`. En mémoire, par process : à revoir si l'API passe sur plusieurs instances. IP lue dans `X-Forwarded-For` seulement si `TRUST_PROXY=true` (`clientIp`, `src/plugins/client-ip.ts`).
- **Rate limit de Better Auth** : actif en plus du nôtre sur `/api/auth/*`, dans tous les environnements (`rateLimit.enabled` dans `authOptions`), avec ses règles par défaut (3 tentatives de connexion par 10 s et par IP). Réponse 429 au format Better Auth. Compteurs sur `FixedWindowStore` (`customStorage`, un store par instance : celui de Better Auth est une `Map` partagée par tout le module). Better Auth ne lit l'IP que dans un en-tête : le plugin `authentication` écrit celle de `clientIp` dans `x-typomaniac-client-ip` (`CLIENT_IP_HEADER`, écrasé si le client l'envoie), seul en-tête lu (`advanced.ipAddress.ipAddressHeaders`). Sans serveur (`app.handle`), Better Auth retombe sur `127.0.0.1` : un seul compteur.
- **Body** : 1 Mo max sur le `Content-Length` déclaré (`body-limit`, 413 au format API). Bun garde une limite dure de 4 Mo (`maxRequestBodySize`) qui répond un 413 vide : elle doit rester au-dessus de la nôtre.

## Auth

Better Auth, OAuth uniquement en production (ADR `docs/adr/0001-…`, vocabulaire User / Account / Session dans `CONTEXT.md` à la racine).

- **Instance** : `createAuth` (`src/modules/auth/service.ts`) avec l'adapter Drizzle, appelé par `src/index.ts` avec l'env parsé et injecté via `AppConfig.auth`. `app.ts` ne dépend que du type (`AuthHandler`). Les options (Session, cookies, `trustedOrigins`, fournisseurs) sont dans `authOptions`, partagées avec les tests.
- **Montage** : `src/modules/auth/index.ts` route `/api/auth/*` vers le handler (`basePath` `/api/auth`). Pas de `.mount("/auth", …)` : il retire le chemin de l'URL et Better Auth route sur l'URL complète.
- **Macro `auth`** : `{ auth: true }` sur une route exige une Session ; sans Session valide, `ApiError("UNAUTHORIZED")` ; avec, `user` et `session` dans le contexte. Elle renvoie au navigateur les cookies que Better Auth rafraîchit (cache de Session, prolongation).
- **Session** : en base, 30 jours, prolongée à l'usage (au plus une fois par jour), cache de 5 min dans le cookie `session_data`. Cookies httpOnly, `SameSite=Lax` (front et API sur deux sous-domaines du même site). CORS avec `credentials: true`, `trustedOrigins` = `CORS_ORIGIN`.
- **Env** : `BETTER_AUTH_SECRET` (32 caractères min, `openssl rand -base64 32`) et `BETTER_AUTH_URL` (URL publique de l'API) obligatoires. Fournisseurs GitHub, Google et Discord (`<FOURNISSEUR>_CLIENT_ID` / `_CLIENT_SECRET`) : les deux renseignés, il est activé ; aucun (vide = absent), il est désactivé ; un seul, `parseEnv` lève une erreur et le serveur ne démarre pas. `parseEnv` en dérive `socialProviders` ; un fournisseur non configuré répond 404 à la connexion. Callback à déclarer chez le fournisseur : `<BETTER_AUTH_URL>/api/auth/callback/<provider>`.
- **Email / mot de passe (dev uniquement)** : actif hors production, sans vérification ni envoi d'email (`emailAndPassword.enabled = !isProduction`, `AuthSettings.isProduction`), pour ouvrir plusieurs Users et tester le Duel (ADR `docs/adr/0005-…`). En production, `/sign-up/email` et `/sign-in/email` sont dans `disabledPaths` : 404.
- **Liaison de comptes** : se connecter avec un second fournisseur rattache un nouvel Account au User qui a le même email. GitHub et Google sont de confiance (`trustedProviders`) ; Discord n'est rattaché que s'il marque l'email vérifié, sinon la connexion est refusée. Le User existant doit lui-même avoir un email vérifié (`requireLocalEmailVerified`, défaut de Better Auth).
- **Handle** (vocabulaire dans `CONTEXT.md`) : champ additionnel `handle` du User (`user.additionalFields`, `input: false` : jamais saisi à l'inscription, `unique`), en minuscules, null tant qu'il n'est pas choisi. Règles dans le paquet partagé `handle` (`packages/handle`, `parseHandle` : `too-short`, `too-long`, `invalid-chars`, `reserved` ; `suggestHandle` pour le pré-remplissage du front). `src/modules/handle/service.ts` ajoute `taken`. Routes (macro `auth`) : `GET /api/handles/availability?handle=` (`{ available: true, handle }` ou `{ available: false, reason }` ; son propre Handle est disponible) et `PUT /api/me/handle` (renvoie le User comme `/api/me` ; refus en 422 `VALIDATION_FAILED` ou 409 `CONFLICT`, la raison dans `details[0].message`, `path` `/handle`). Un Handle pris entre la vérification et l'écriture : la contrainte unique refuse, relu comme `taken` (409), pas un 500. Après l'écriture, la Session est relue en base (`readSession(…, { fresh: true })`, `disableCookieCache`) pour réécrire le cookie `session_data` : `/api/me` voit le Handle aussitôt. `/api/me` expose `handle`.
- **Users** : `AppConfig.users` (`Users`, `src/modules/user/users.ts`) lit et écrit les Users hors Session (qui peut dater de 5 min, cookie cache) : `profileOf` (Handle et avatar), `profilesOf` (ceux d'une liste d'ids qui ont un Handle, pour les Friends), `idOfHandle`, `setHandle`, `searchHandles`. `authUsers(auth, { searchHandles })` passe par l'adapter de Better Auth (`$context`) : même code sur Drizzle et sur l'adapter mémoire des tests ; un test peut l'envelopper pour forcer une course. Sauf la recherche par préfixe, injectée à part : le `starts_with` de l'adapter est un `LIKE` où `_` est un joker. En prod `drizzleHandleSearch(db)` (`src/modules/user/drizzle-handle-search.ts`, `LIKE` échappé, tri `COLLATE "C"`) ; dans les tests `testUsers(auth)` (`src/test-app.ts`), qui filtre et trie en mémoire dans le même ordre.
- **Recherche de Users** : `GET /api/users/search?handle=` (macro `auth`, `src/modules/user/`). Il faut un Handle soi-même (sinon 403 `FORBIDDEN`) et au moins 2 caractères (sinon 422). Préfixe insensible à la casse, 10 résultats au plus, Handle exact en tête puis ordre alphabétique (ordre des octets), jamais le User qui cherche ni un User sans Handle ; un préfixe hors `a-z 0-9 _` ou trop long ne trouve rien. Chaque résultat : `id`, `handle`, `image`, `relation` (`none`, `friend`, `request-sent`, `request-received`, lue dans le `FriendStore`), jamais name ni email. Rate limit dédié par User (`AppConfig.searchRateLimit`, `keyedRateLimit` de `src/plugins/rate-limit.ts`, 30 par minute en prod), en plus du global par IP.
- **Friend requests et Friends** (vocabulaire dans `CONTEXT.md`, `src/modules/friend/`) : routes (macro `auth`, Handle requis sinon 403) `GET /api/friends` (par Handle), `DELETE /api/friends/:userId` (retirer, sans l'accord de l'autre), `GET /api/friend-requests` (`{ received, sent }`, plus récentes d'abord), `POST /api/friend-requests` (`{ userId }`), `DELETE /api/friend-requests/sent/:userId` (annuler), `POST /api/friend-requests/received/:userId/accept`, `DELETE /api/friend-requests/received/:userId` (refuser, sans prévenir l'envoyeur, qui peut redemander). Chaque User n'y montre que `id`, `handle`, `image` ; chaque action renvoie `{ relation }`, où en est le User avec l'autre. Règles dans `service.ts` : pas à soi-même, à un User qui existe et a un Handle, pas à un Friend, pas de doublon ; une Friend request croisée fait deux Friends aussitôt (c'est un accept), même envoyée au même instant que l'autre (`addRequest` renvoie `crossed` ; en Drizzle, sous un verrou `pg_advisory_xact_lock` sur la paire) ; plafonds `MAX_FRIENDS` (200, des deux côtés à l'accept) et `MAX_SENT_REQUESTS` (50 envoyées en attente), comptés avant l'écriture (deux accepts simultanés peuvent le dépasser d'un). Refus : 4xx avec la règle dans `details[0].message`, `path` `/userId` (`FRIEND_REFUSALS` de `model.ts`, type `FriendRefusal` réexporté par `app.ts` pour le front) : `self` 422, `user-not-found` / `request-not-found` / `not-friends` 404, `already-friends` / `already-requested` / `request-limit` / `friend-limit` / `their-friend-limit` 409. Rate limit dédié sur l'envoi, par User (`AppConfig.friendRequestRateLimit`, 20 par minute en prod). Stockage : `FriendStore` (`store.ts`), lectures et écritures seulement ; tables `friend_request` (clé sender + recipient) et `friendship` (une ligne par paire, `user_a_id` < `user_b_id`, `orderedPair`), en cascade avec le User (`schema.ts`). En prod `drizzleFriendStore(db)` (`drizzle-store.ts`, accepter = suppression de la demande + écriture de l'amitié dans une transaction ; vérifié à la main sur le Postgres de dev, pas de test automatisé, comme le store des Duels) ; dans les tests `memoryFriendStore()` (`src/test-app.ts`). Après chaque écriture, le service notifie `FriendEvents` (`deps.events`), sans attendre : `requestSent`, `requestRemoved` (annulée ou refusée), `friendsAdded` (accept ou demande croisée), `friendsRemoved`.
- **Presence et push en direct** (`src/modules/friend/live.ts`, `FriendsLive`, une instance créée par `createApp`, notifiée par le module friend via `events` (avec `DuelQueue` pour `friendsRemoved`) et passée au module duel) : tout en mémoire, rien en base. Presence dérivée : hors ligne sans connexion, `in-duel` de l'appariement (Countdown compris) à la fin du Duel (`DuelQueue` le dit via `onDuel`), en ligne sinon (Queue comprise). La route `/api/duel` lui passe chaque connexion (`connect` / `disconnect`). Chaque User connecté a ses Friends lus une fois dans le store (les autres connexions attendent la même lecture ; les notifications reçues pendant la lecture sont rejouées après), puis tenus à jour par les notifications. La Presence d'un User part aux `#watchers` : les Users connectés dont les Friends sont lus et le comptent (tenu du côté de ceux qui regardent, sans attendre la lecture du User) ; il ne part qu'aux changements (première connexion, dernière fermée, début et fin de Duel). Messages serveur (`FriendLiveModel.friendMessage` de `friend/model.ts`, dans l'union `ServerMessage`) : `friends-snapshot` (à chaque connexion, après la place : Presence de chaque Friend, `requestsReceived`), `presence`, `friend-request-received` et `friend-request-removed` (au destinataire seul, toutes ses connexions : un refus n'est jamais dit à l'envoyeur), `friend-added` (aux deux, avec la Presence de l'autre), `friend-removed` (aux deux). Les messages qui lisent le store (compte des Friend requests reçues) partent dans l'ordre demandé, par User (`#later`), et seulement à un User connecté ; une lecture en échec est loggée `friends not told`. Tests : `src/modules/friend/live.test.ts`, vraies sockets + routes HTTP sur `listen(0)`.
- **Schéma** : `src/database/auth-schema.ts` est généré par la CLI (`bunx auth@latest generate`, avec une config qui construit l'instance) ; le régénérer quand les options ou les plugins changent, puis `db:generate`.
- **Tests** : `betterAuth({ ...authOptions(…), database: memoryAdapter(…), plugins: [testUtils()] })`, puis `(await auth.$context).test.login({ userId })` pour obtenir le cookie d'une Session. Pour la connexion sociale et la liaison : des fournisseurs factices (`verifyIdToken` + `getUserInfo`) et `POST /api/auth/sign-in/social` avec `idToken`, qui passe par la vraie logique User / Account sans aller-retour OAuth. Toutes ces requêtes viennent de la même IP : une instance partagée par plusieurs tests de connexion désactive le rate limit de Better Auth (`rateLimit.enabled: false`), testé à part.

## Duel (WebSocket)

État temps réel en mémoire, une seule instance (ADR `docs/adr/0003-…`, vocabulaire Duel / Queue / Countdown dans `CONTEXT.md`).

- **Route** : `src/modules/duel/index.ts`, WebSocket `/api/duel` monté en dernier par `createApp`. C'est la connexion temps réel de toute l'app (ADR `docs/adr/0007-…`) : le front l'ouvre sur toutes les pages dès qu'une Session existe. La macro `auth` s'applique à l'upgrade : sans Session valide, 401 au format API et pas de connexion.
- **Service** : `DuelQueue` (`src/modules/duel/service.ts`, la Queue et les Users connectés), indépendant d'Elysia (la route lui passe une `Connection`). Plusieurs connexions par User (un onglet chacune, `#connections`), une seule place, jouée sur une seule d'entre elles (`#playing`) : celle qui a envoyé `join-queue` ou `resume-duel` (n'importe quelle connexion peut la prendre ; celle qui la jouait reçoit `elsewhere`). `leave-queue`, `keystrokes` et `leave-duel` des autres connexions sont ignorés. Les connexions qui ne jouent pas reçoivent la place à l'ouverture et à chaque changement : `idle`, ou `elsewhere` (`place` `queue` / `duel`) ; celle qui joue l'apprend par ses propres messages (`queued`, `duel-found`, `duel-ended`…). Fermer une connexion qui ne joue pas ne change rien. **Handle** : à `join-queue`, le profil est relu (`Users.profileOf`, pas le User de la Session) ; sans Handle → `handle-required`, pas de place dans la Queue ; profil illisible → loggé `profile not read`, hors de la Queue. `queued` part une fois le Handle lu, suivi de `queue-status` (`joinedAt`, gardé si le User rejoint depuis un autre onglet ; `serverTime` ; `size`, les Users de la Queue au Handle lu, lui compris ; `estimatedWait`, Estimated wait en ms par `estimatedWait` du package ranked sur les attentes des `ESTIMATED_WAIT_PAIRINGS` derniers appariements de la Queue, Challenges exclus, null sans appariement). À chaque entrée ou sortie, `queue-status` repart à tous les Users de la Queue au plus une fois par `QUEUE_STATUS_MS` (1 s, un seul `clock.at` en attente, `#statusDue`). Le client de test le range à part (`nextQueueStatus()`, `queueStatuses()`). L'adversaire est désigné par ce Handle et son avatar, jamais par son name. **Pace** : lue ensuite (`#readPace` : attend l'écriture du dernier Duel du User, puis `readPace(store, userId)` de `modules/duel/store.ts`, le `paceOf` du moteur ; lecture en échec → loggée `pace not read`, Pace par défaut), figée pour le Duel ; un User n'est apparié qu'une fois sa Pace lue, sans bloquer ceux derrière lui. `duel-found` et `duel-resumed` portent `pace` et `opponentPace`, et `opponentRank` (rang de l'adversaire avant le Duel, montré pendant le Countdown, jamais le MMR ; null pour un Challenge ou une Rating illisible). Appariement dans l'ordre d'arrivée de deux Users distincts (parmi ceux dont le profil, la Pace et la Rating sont lus), chacun avec le premier arrivé après lui dont l'écart de MMR tient dans la fenêtre (`matchWindow` du package ranked, selon l'attente depuis `join-queue` de celui qui attend le plus : ±100, +50 toutes les 5 s, illimitée à 30 s ; sans Rating, tout MMR tient). Ceux qui restent sont retentés au prochain élargissement (`nextWidening`, un seul `clock.at` en attente, `#nextPairAt`). Pour chaque Duel : Seed tirée par le serveur, anglais, Word list version courante, `time` 30 s, `startsAt` = maintenant + 3 s, `serverTime` pour le décalage d'horloge du client.
- **Duel en cours** : `RunningDuel` (`src/modules/duel/running-duel.ts`), un par paire, gardé par `DuelQueue` pour chaque User jusqu'à sa fin (`join-queue` ignoré avant). Chaque Keystroke d'un lot passe par `acceptKeystroke` du moteur (arrivée = maintenant − `startsAt`, tolérance `END_TOLERANCE_MS` après la fin) : les acceptés sont relayés à l'adversaire (`opponent-keystrokes`) ; un seul rejet dans le lot renvoie au client `resync` (ses Keystrokes acceptés, le nombre reçu de lui, ceux de l'adversaire), le client garde ce qu'il a envoyé au-delà de ce nombre.
- **Fin** : programmée à l'appariement via `clock.at`, à `startsAt` + 30 s + `END_TOLERANCE_MS`. Le serveur calcule les deux Results (`computeResult` sur les Keystrokes acceptés), les deux Scores (`computeScore`, chacun à la Pace du joueur) et l'issue (`duelOutcome` du moteur : Score, puis accuracy, sinon Draw ; un Forfeit décide quel que soit le Score), envoie à chacun `duel-ended` (`duelId`, voir Persistance ; son issue `win` / `loss` / `draw`, `forfeit`, son Result et son Score — points, meilleur Combo, Bursts —, ceux de l'adversaire, l'adversaire) une fois le Duel écrit, et libère alors les deux Users : leurs Keystrokes sont ignorés, `join-queue` les remet en Queue. Un Duel ne finit qu'une fois (`#finish` ignore un Duel déjà terminé) ; un joueur sans connexion qui joue à la fin la reçoit au prochain `resume-duel` d'une de ses connexions (jusque-là, sa place reste `elsewhere` `duel`) ; `join-queue` l'oublie.
- **Historique** : un Duel écrit ne garde que les ids des Users, jamais leur Handle : toute lecture de l'historique passe par l'id pour afficher le Handle actuel ; changer de Handle garde ses Duels.
- **Duel history** (vocabulaire dans `CONTEXT.md`, `src/modules/duel-history/`) : `GET /api/duels?before=<curseur>` (macro `auth`) → `{ duels, next }`, 20 par page (`DUEL_HISTORY_PAGE`), du plus récent au plus ancien, par `ended_at` puis id. Curseur `<endedAt ms>:<id>` du dernier Duel de la page (`next`, null sur la dernière) ; malformé → 422. Chaque élément : `id`, `endedAt`, `opponent` (`{ handle, image }` lu par id dans `Users.profilesOf`, Handle actuel ; null si le User est supprimé), `outcome` vu du lecteur (`win` / `loss` / `draw` : le winner gagne, l'autre perd, Forfeit compris), `forfeit`, `score` / `opponentScore` (null pour un Duel d'avant le Score), `wpm` / `opponentWpm` (null si l'adversaire est supprimé), `tp` (TP que le Duel a fait bouger pour le lecteur, `duel_player.tp_delta` ; null pour un Challenge, en Placement ou avant la ranked ; jamais le MMR). Lecture `DuelStore.history(userId, { before, limit })` : en Drizzle, jointure sur la ligne de joueur de l'adversaire (partie en cascade avec son User), index `duel_player_userId_idx` suffisant ; en mémoire, `memoryDuelStore().deleteUser` reproduit la cascade. **Replay** : `GET /api/duels/:duelId` (macro `auth`) → le Duel vu du lecteur, pour le rejouer côté client : Seed, Language, Word list version, `seconds`, `startsAt`, `endedAt`, `outcome` / `forfeit` comme la Duel history, puis `me` et `opponent` (Handle et avatar actuels, Result, `pace` — null avant la Pace historique —, `score` — null avant le Score —, Keystrokes acceptés ; `opponent` null si son User est supprimé). 404 `NOT_FOUND` aussi bien pour un Duel inexistant que pour un Duel que le lecteur n'a pas joué. Lecture `DuelStore.playedDuel(userId, duelId)` (`PlayedDuel`, null si ce User n'y a pas joué) : en Drizzle, le Duel joint à ses lignes de joueur.
- **Profile et Stats** (vocabulaire dans `CONTEXT.md`, `src/modules/profile/`) : `GET /api/users/:handle/profile` (macro `auth`, limite globale seulement) → `{ handle, image, stats }`, jamais name ni email. Handle comparé sans casse via `Users.idOfHandle` puis `profileOf` ; inconnu ou ancien Handle → 404 `NOT_FOUND`. `stats` : `duels`, `record` (`wins`, `losses`, `draws` vus du User, Forfeits compris), `averages` (`wpm`, `accuracy`, null sans Duel), `records` (`wpm` ; `score` et `combo`, null sans Duel écrit depuis le Score), `progression` (Progression : `{ endedAt, wpm, raw, accuracy, consistency }` des N derniers Duels hors Forfeit, du plus ancien au plus récent ; N par `?window=50|200|all`, 50 par défaut, autre valeur → 422 ; la fenêtre ne touche que la Progression, lue par `DuelStore.progression(userId, limit)`). Calculées par `DuelStore.stats(userId)` : en Drizzle une seule requête d'agrégat sur les lignes de joueur du User (une défaite = ni victoire ni Draw : un gagnant supprimé laisse `winner_id` null) ; les Duels contre un User supprimé comptent.
- **Classement** (vocabulaire dans `CONTEXT.md`, `src/modules/leaderboard/`) : `GET /api/leaderboard` (macro `auth`) → `{ entries, me }`. `entries` : les `LEADERBOARD_LIMIT` (100) premiers Users hors Placement, triés par `byStanding` du package ranked (Tier, Division puis TP ; Maître par TP), égalités par id ; chacun `position` (dès 1), `handle`, `image`, `rank` (`DuelModel.standing`), jamais le MMR, le name ni l'email. Un User sans Handle garde sa place mais n'est pas listé. `me` : la ligne du lecteur où qu'il soit (au-delà des 100 compris), null en Placement ou sans Rating. Lecture `DuelStore.leaderboard(limit)` et `leaderboardPosition(userId)` : en Drizzle, `stepOf` en SQL (`array_position` sur `TIERS`) et `row_number()` pour la position (vérifié à la main sur le Postgres de dev) ; en mémoire, même tri.
- **Activity** (vocabulaire dans `CONTEXT.md`, `src/modules/activity/`) : `GET /api/activity` (macro `auth`) → les `ACTIVITY_LIMIT` (50) dernières Activities, les plus récentes d'abord, union discriminée par `type` : `duel` (`id`, `at` = fin, `forfeit`, `friend` et `opponent` avec Handle, avatar, wpm et issue vue de chacun ; `opponent` null si supprimé) et `friendship` (`id` = paire ordonnée, `at` = début, `friend`, `other`). `friend` est toujours un Friend actuel du lecteur. Rien d'écrit : dérivée à chaque lecture de `friendIds`, `DuelStore.recentDuelsOf` (chaque Duel une fois, même joué par deux Friends) et `FriendStore.recentFriendshipsOf` (colonne `created_at` de `friendship`) ; une amitié retirée retire donc les Activities de l'ex-Friend, une nouvelle montre son passé. Sans Friend (ou sans Handle), liste vide. Le lecteur n'y voit ses propres Duels que contre un Friend, ses amitiés seulement avec ses Friends. **En direct** : message serveur `activity-added` (`ActivityModel.activityMessage`, dans l'union `ServerMessage`, `{ activity }` au même format), envoyé par `FriendsLive` (`#tellActivity` : aux `#watchers` de l'un ou l'autre des deux Users, chacun une fois, vu de lui par `duelActivity` / `friendshipActivity` du service, profils lus une fois ; lecture en échec loggée `activity not told`). Un Duel part une fois écrit (`DuelQueue` → `onDuelSaved`, jamais si l'écriture a échoué ou pris trop de temps) ; une amitié à `friendsAdded` (`at` = `Clock.now()`). Une fin d'amitié n'a pas de message : `friend-removed` suffit au front pour relire. Arrivée en ligne : `friend-arrived` (`ActivityModel.arrivalMessage`, `{ arrival: { id, at, friend } }`), envoyé par `FriendsLive.#tellArrival` aux watchers quand la première connexion fait passer le User de hors ligne à en ligne (jamais en sortant d'un Duel) ; ni écrit ni renvoyé par `GET /api/activity`. Tests : `src/modules/activity/live.test.ts` (client de test : `nextActivity()`, `settleActivity()`, `nextArrival()`, `settleArrivals()`).
- **Persistance** : à sa fin (temps écoulé ou Forfeit), `#finish` écrit le Duel une fois via `AppConfig.duelStore` (`DuelStore`, `src/modules/duel/store.ts`), et n'envoie `duel-ended` qu'une fois l'écriture terminée : `duelId` = l'id du Duel écrit (le Replay à ouvrir), `null` si l'écriture a échoué. L'écriture est bornée à `SAVE_TIMEOUT_MS` (5 s, sur la `Clock`) : au-delà, `duel-ended` part avec `null` (loggé `finished duel not saved in time`), une base qui pend ne bloque pas les joueurs. Pendant l'écriture (`#beingWritten`), le Duel reste la place des deux joueurs (`isInDuel`, `elsewhere` `duel`, `join-queue` ignoré, Presence `in-duel`) ; un `resume-duel` y reçoit la fin quand elle part. `DuelRecord` = le `Duel` du protocole + `mode`, `endedAt`, issue `win` / `draw` / `forfeit`, `winnerId` (null pour un Draw) et, par joueur, son Result, sa Pace, son Score et ses Keystrokes acceptés (rejoués avec Seed + Language + Word list version et la Pace, ils redonnent le Result et le Score). Colonnes `score`, `best_combo` et `bursts` de `duel_player` nulles pour les Duels écrits avant le Score : leur issue reste celle de l'époque, au wpm ; `pace` nulle pour ceux écrits avant la Pace historique. `DuelStore.recentWpms` lit les wpm des derniers Duels d'un User (anciens compris), du plus récent au plus ancien, ordonnés par `ended_at` ; `GET /api/me/pace` (macro `auth`) en donne la Pace pour le Run solo. Tables `duel` et `duel_player` (`src/modules/duel/schema.ts`, Seed en `bigint` : c'est un uint32). En prod `drizzleDuelStore(db)` (`src/modules/duel/drizzle-store.ts`, une transaction) ; dans les tests `memoryDuelStore()` (`src/test-app.ts`, les Duels écrits dans `saved`). Un échec d'écriture est loggé (`finished duel not saved`), les joueurs reçoivent leur fin quand même. Un Duel en cours au redéploiement n'est jamais écrit.
- **Ranked** (vocabulaire dans `CONTEXT.md`, règles pures dans `packages/ranked`, ADR `docs/adr/0008-…`) : à `join-queue`, après la Pace, la Rating (MMR + rang) est lue par `DuelStore.ensureRating(userId, initial)`, créée au premier join depuis la Pace (`seedMmr`, 5 Placements) ; lecture en échec → loggée `rating not read`, Duel non classé. `PacedUser.rating` : null pour un Challenge (jamais classé). À la fin, si les deux ont une Rating, `RunningDuel` applique `rateDuel` à chacun (issue vue de lui : Forfeit = défaite pleine / victoire pleine, Draw = 0,5, contre le MMR de l'autre avant le Duel) ; `DuelPlayerRecord.rated` = `{ before, after, tp }` (sinon null). `save` écrit dans la même transaction `duel.ranked`, `duel_player.tp_delta` / `mmr_delta` et la nouvelle ligne `ranked_rating` (upsert). `duel-ended.ranked` = `{ tp, previousRank, rank }` (`tp` null en Placement), jamais le MMR ; null pour un Challenge et quand le Duel n'est pas écrit (échec ou délai : rien n'a bougé). La Rating du Duel suivant attend l'écriture du dernier, comme la Pace. En mémoire (`memoryDuelStore().ratings`), un test peut poser une Rating avant le join. Le store Drizzle des Ratings est vérifié à la main sur le Postgres de dev.
- **Connexion** : une nouvelle connexion ne joue rien et reçoit la place (`elsewhere` ou `idle`). Contrairement à avant le multi-onglets, le serveur ne reprend plus le Duel tout seul à la connexion : un onglet ouvert ailleurs dans l'app ne doit pas le prendre. Pour jouer le Duel (reconnexion, rechargement, autre onglet), la connexion envoie `resume-duel` → `duel-resumed` (Duel, adversaire, `serverTime`, état complet comme `resync`, `opponentConnected`), ou la fin manquée (`duel-ended`) ; sinon, ignoré.
- **Challenge** (vocabulaire dans `CONTEXT.md`, `src/modules/challenge/`) : `Challenges` (`service.ts`), créé et possédé par `DuelQueue`, qui lui sert d'arène (`ChallengeArena` : connexions, `isInDuel`, `readPace`, `startDuel`). `DuelQueue` est construit par `createApp` (plus par le module duel) : les notifications du module friend lui passent `friendsRemoved`. Tout en mémoire. Messages client (dans l'union `ClientMessage`, acceptés depuis n'importe quelle connexion) : `send-challenge` (`userId`), `cancel-challenge`, `accept-challenge`, `decline-challenge` (`challengeId`). Messages serveur (`ChallengeModel.challengeMessage`, à toutes les connexions des deux Users) : `challenges-snapshot` (à chaque connexion, après la place : `sent`, `received`), `challenge-received`, `challenge-sent`, `challenge-ended` (`accepted`, `declined`, `cancelled`, `expired`, `unavailable`), et `challenge-refused` à la seule connexion qui envoie (`CHALLENGE_REFUSALS` : `self`, `already-challenging`, `offline`, `in-duel` — l'un des deux —, puis après lecture `handle-required` et `not-friends`, relus dans `Users` et le `FriendStore`). Expirations et `serverTime` par la `Clock`, 30 s (`CHALLENGE_MS`). Au plus un Challenge envoyé par User (un envoi en cours de vérification compte), plusieurs reçus. Accepter : revérifie connexions et Duels, puis lit l'amitié et les deux Paces, revérifie, termine le Challenge (`accepted`) et `startDuel` (retire les deux de la Queue, joue sur la connexion qui accepte et celle qui a envoyé — une autre du même User si elle est fermée —, même `#start` que l'appariement : format, Countdown, Pace, écriture en fin). Un Challenge finit `unavailable` quand l'un des deux entre en Duel (`enteredDuel`, appelé par `#start` : accepter annule donc les autres), n'a plus de connexion (`left`) ou que l'amitié est retirée. Tests : `src/modules/challenge/socket.test.ts` (client de test : `nextChallenge()`, `settleChallenges()`).
- **Forfeit** : `leave-duel` = Forfeit immédiat ; plus de 40 Keystrokes acceptés en moins d'une seconde (dates client) = Forfeit. Fermeture de la connexion qui joue en Duel : l'adversaire reçoit `opponent-disconnected`, et le joueur a `RECONNECT_GRACE_MS` (10 s) pour revenir, même si d'autres connexions à lui restent ouvertes (jeton par déconnexion : une seconde déconnexion a ses propres 10 s) ; `resume-duel` depuis n'importe laquelle de ses connexions → `duel-resumed` pour elle, `opponent-reconnected` pour l'adversaire ; sinon Forfeit. Passer le Duel à un autre onglet n'est pas une déconnexion : l'adversaire n'en sait rien.
- **Protocole** : `src/modules/duel/model.ts`, schémas TypeBox, types `ClientMessage` / `ServerMessage` réexportés par `app.ts` pour le front. Les messages client sont validés à la main (`clientMessage.Check`), pas via le `body` de la route : Elysia répondrait un corps d'erreur HTTP hors protocole ; un message invalide reçoit `invalid-message`. Taille bornée par `websocket.maxPayloadLength` (`MAX_DUEL_MESSAGE_SIZE`, sur l'instance racine) : au-delà, Bun ferme la connexion.
- **Horloge** : `AppConfig.clock` (`src/lib/clock.ts`) : `now()` et `at(time, callback)` pour programmer un événement. `systemClock` en prod (`setTimeout`) ; dans les tests, `manualClock` (`src/test-app.ts`), dont `set(time)` avance l'heure et lance les callbacks échus.
- **Tests** : `src/modules/duel/index.test.ts`, `createApp` sur un vrai `listen(0)`, Sessions via `signIn` (`src/test-app.ts`, helpers partagés avec `app.test.ts`) et le client `WebSocket` de Bun avec l'en-tête `cookie`. Pas de lib DOM dans `tsconfig.json` : elle masquerait la signature de Bun (`headers`). Pour prouver qu'aucun message n'arrive, `settle()` fait un aller-retour (message invalide → `invalid-message`) au lieu d'attendre. Le client de test (`openClient`, `src/test-app.ts`) range à part les messages des Friends (`nextFriends()`, `settleFriends()`) : les tests de Queue et de Duel lisent `next()` sans eux.

## OpenAPI

- `@elysiajs/openapi`, monté par `src/plugins/api-docs.ts` : spec sur `/api/openapi/json`, référence Scalar sur `/api/openapi`. **Désactivé en production** (404).
- La spec est générée depuis les schémas TypeBox des routes : toute route publique déclare son `response` et un `detail` (`summary`, `tags`). Un nouveau tag se déclare dans `documentation.tags`.
- **Endpoints Better Auth** : la route `/auth/*` est cachée (`detail.hide`) ; `api-docs` fusionne à la place, dans la réponse de `/api/openapi/json` (`onAfterHandle`), le schéma du plugin `openAPI` de Better Auth (`auth.api.generateOpenAPISchema()`, appelé côté serveur à la première requête puis mémorisé) : chemins préfixés par `/api/auth`, tous sous le tag `Auth` (avec `/api/me`), `components` (schémas User/Session/…, `securitySchemes`) ajoutés aux nôtres. Les routes HTTP du plugin (`/api/auth/open-api/generate-schema`, `/api/auth/reference`) sont dans `disabledPaths` : 404 partout. `generator`, bien que typé comme export de `better-auth/plugins`, n'existe pas au runtime : passer par le plugin.
- La page Scalar a sa propre CSP (bundle jsdelivr, styles inline), posée après `security-headers` ; la version de Scalar est épinglée (`SCALAR_VERSION`).

## Erreurs

Toute erreur sort au même format, défini dans `src/lib/errors.ts` et réexporté par `app.ts` pour le front (`import type { ApiErrorBody } from "api"`) :

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "…",
    "requestId": "…",
    "details": [{ "path": "/name", "message": "…" }]
  }
}
```

- Codes : `BAD_REQUEST` 400, `UNAUTHORIZED` 401, `FORBIDDEN` 403, `NOT_FOUND` 404, `CONFLICT` 409, `PAYLOAD_TOO_LARGE` 413, `VALIDATION_FAILED` 422, `TOO_MANY_REQUESTS` 429, `INTERNAL_SERVER_ERROR` 500. Un nouveau cas se déclare dans `ERRORS`.
- Dans un handler ou un service : `throw new ApiError("FORBIDDEN", "message lisible")`. Le message part au client : jamais de détail interne.
- L'error-handler traduit aussi les erreurs d'Elysia (route inconnue, JSON invalide, validation avec `details`) et un `throw status(409, …)` (code déduit du status, payload ignoré). Une réponse qui viole son propre schéma est un 500.
- Tout le reste devient `INTERNAL_SERVER_ERROR` générique ; les 5xx sont loggés avec stack et `requestId`.
- Un `return status(…)` n'est **pas** une erreur pour Elysia : il ne passe pas par l'error-handler. Pour une erreur, `throw`.
- **Exception** : les routes `/api/auth/*` répondent au format d'erreur de Better Auth (`{ message, code }`), leurs réponses ne passent pas par l'error-handler. `/api/me` et toute route protégée par la macro `auth` restent au format unifié.

## Eden Treaty

- `src/app.ts` construit l'app (`createApp`) et exporte `type App`, consommé par le front via `import type { App } from "api"` (champ `exports` du `package.json`). `src/index.ts` ne fait que migrer et `listen()`.
- Routes chaînées sur une seule expression, sinon Eden perd l'inférence.
- Le préfixe apparaît dans l'arbre Eden : le front exporte `treaty<App>(url).api` (`apps/frontend/src/api/client.ts`), les appels s'écrivent `api.health.get()`.
- `app.ts` ne doit pas importer `env.ts` : le front typecheck ce graphe de fichiers.
