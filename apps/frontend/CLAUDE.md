# apps/frontend

Front React 19 + Vite 8 (React Compiler Rust d'Oxc via `react({ compiler })` de `@vitejs/plugin-react`, pas de Babel). Point d'entrée : `src/main.tsx`.

## Skill obligatoire

**Avant de créer, modifier ou relire un composant, un hook ou tout code React**, invoquer le skill `vercel-react-best-practices` et appliquer ses règles. Pas d'exception pour les petites modifications.

## Architecture

- **Routing** : TanStack Router en file-based (`src/routes/`, plugin Vite, `autoCodeSplitting`). `src/routeTree.gen.ts` est généré (ignoré par oxlint/oxfmt), ne pas l'éditer. Un fichier de route ne déclare que `Route` ; ses composants vivent dans `src/pages/` (sinon `react/only-export-components` casse, et exporter le composant depuis la route désactive le code-splitting).
- **État serveur** : React Query, jamais dans Zustand. Chaque ressource expose des `queryOptions()` dans `src/api/<ressource>.ts`, appels via le client Eden `api` et `unwrap` (`src/api/client.ts`) qui lève une `ApiError`. Les loaders font `context.queryClient.ensureQueryData(opts)`, les composants `useSuspenseQuery(opts)`. Exception : un élément d'appoint qui ne doit jamais faire attendre ce qui l'entoure (`RealtimeConnection`, qui lit le User ; le Face-off, la Queue, la Match proposal et le HUD du Duel, qui lisent son avatar ou son Handle ; « En ligne » de la barre latérale, qui lit les Friends par `useOnlineFriends`) lit via `useQuery` et n'affiche rien tant qu'il n'a pas de données. Après une action, invalider via les `queryKey` des `queryOptions`, jamais des clés recopiées. `defaultPreloadStaleTime: 0` : le cache est géré par Query.
- **Erreurs de l'API** : **TOUJOURS suivre le fichier d'erreurs de l'API**, `apps/api/src/lib/errors.ts` (section Erreurs de `apps/api/CLAUDE.md`). Toute erreur HTTP a le format `ApiErrorBody` (`{ error: { code, message, requestId, details? } }`) ; codes et types viennent de `api/errors` (`ERRORS`, `ErrorCode`, `ErrorDetail`, sans dépendance serveur), jamais redéclarés ni devinés. `ApiError` (`src/api/client.ts`, levée par `unwrap`, ou construite depuis `result.status` et `result.error.value` hors `unwrap`) valide le corps contre ce format et expose `code` (null si le corps n'est pas au format ou le code inconnu), `requestId`, `details`. On branche sur `error.code` (`"NOT_FOUND"`, `"TOO_MANY_REQUESTS"`…), jamais sur `error.status` ; la règle d'un refus se lit par `refusalAt(error, "/handle")`. Jamais le `message` de l'API affiché au User : le texte est écrit côté front. Seule exception, celle de l'API : `/api/auth/*` répond au format de Better Auth.
- **Connexion temps réel** (ADR 0007) : `src/stores/connection-store.ts`, la WebSocket de l'app (`api.duel`), une par onglet, ouverte par `RealtimeConnection` (monté dans `RootLayout`, lit le User via `useQuery` : il ne fait jamais attendre la page) dès qu'une Session existe, refermée à la déconnexion, rouverte seule si elle coupe (1 s, doublé à chaque échec, 8 s au plus). Elle tient la place du User (`place`, poussée par le serveur : exception à « état serveur dans React Query », qui vaut pour HTTP) et diffuse les messages (`onServerMessage`) ; `sendToServer` envoie. Le store du Duel s'y branche : `enter` / `exit` quand Duel s'affiche ou non (prendre la place : `join-queue` ou `resume-duel` ; la quitter : `leave-queue` ou `leave-duel`), `claim` pour la reprendre depuis l'écran « ouvert dans un autre onglet ». Elle tient aussi les Friends (`friends`, null jusqu'au `friends-snapshot` de chaque socket, oublié à la perte) : la Presence de chacun (`presences`, un Friend absent est hors ligne) et `requestsReceived`, que lit le badge de Friends dans la barre latérale ; `friendsAfter` applique les messages (logique pure, testée). `LiveFriendLists` (monté dans `RootLayout`) invalide `FRIEND_QUERY_KEYS` quand un message dit que les listes ont changé (`changesFriendLists` : snapshot, Friend request reçue ou partie, Friend ajouté ou retiré) ; `FriendPresence` affiche la pastille sur `/friends`. Et les Challenges (`challenges`, null jusqu'au `challenges-snapshot`, oublié à la perte) : `challengesAfter` (logique pure, testée) ramène chaque `expiresAt` sur l'horloge de l'onglet (`Date.now()`). `src/components/challenge/` : `ChallengeButton` (Défier, sur chaque Friend ; `challengeBlocker` dit pourquoi il est désactivé), et montés dans `RootLayout` `WaitingChallenges` (cartes fixes par-dessus la page : Challenge envoyé annulable, Challenges reçus avec les secondes qui leur restent, Accepter / Refuser), `ChallengeNotices` (toasts : refus d'envoi, Challenge envoyé refusé, expiré ou devenu impossible) et `DuelOnChallenge` : un `duel-found` hors de l'écran de Duel est un Challenge accepté, joué dans cet onglet → Duel choisi (le Run solo en cours est remplacé par un neuf), navigation vers `/`, où `DuelArea` le reprend (`resume-duel`).
- **Replay** (`src/components/replay/`, route `/duels/$duelId`, fichier `duels_.$duelId.tsx` pour ne pas s'imbriquer dans `/duels`) : entièrement côté client, sans le store du Duel ni la WebSocket. `replay-clock.ts` (logique pure, testée) tient le temps de lecture t, play / pause, le seek et la vitesse (0,5×, 1×, 2×) ; `useReplayClock` le fait avancer à chaque frame sur l'horloge injectée (`ClockContext`). À chaque t, `runAt` du moteur rebâtit les deux Runs et `computeScore` les deux Scores, rendus par `RunText` comme en jeu : le Run du côté choisi (`ReplayView`, Toi ou l'adversaire, `viewedSides`) avec le caret de l'autre. La couleur suit le joueur, jamais le Run affiché (`RunTone` : Toi en `caret`, l'adversaire en `opponent-caret`, caret, Burst, choix du picker) ; `ReplayTextTitle` et la teinte du Text disent quel Run s'affiche. Le caret de l'autre joueur porte son initiale (`RunCaret` `label`) ; en Duel live, le Text a son propre rendu (voir HUD du Duel). Un Duel terminé par Forfeit se rejoue jusqu'au Forfeit seulement (`replayDuration` : fin moins début ; le serveur n'accepte aucun Keystroke après), avec « <nom> : abandon à N s » sous la barre de temps (`replayForfeit` : celui qui n'a pas gagné, et quand ; affiché par `ReplayForfeitMarker`). Adversaire supprimé (`opponent` null) : le seul Run du User, sans caret adverse ni toggle, « User supprimé » en en-tête. On y arrive depuis la Duel history, ou depuis l'écran de fin du Duel (`DuelEnded`) : « Revoir » (`ReplayDuelLink`), affiché seulement si `duel-ended` porte un `duelId` (null quand le serveur n'a pas pu écrire le Duel).
- **Duels** (route `/duels`, `src/components/duel-history/`, planche « Duels » du canvas « Layouts et thèmes ») : sous `DuelsHeader`, `DuelHistory` lit `duelHistoryQueryOptions` (infini, chargé par le loader ; la page suivante quand `NextPageSentinel` se voit) et pose deux colonnes (`DuelHistoryColumns` : la liste, 520 px à gauche ; le Duel choisi sur la largeur restante, `sticky`). À droite, `DuelDetails` (clé = id du Duel : chargement et erreur repartent à chaque choix ; `DuelDetailsCard`, `section` nommée par son h2, aussi dans `DuelsPendingPage`) : `DuelDetailsHeader` aussitôt, depuis la ligne (issue en titre, « contre @x · date · Duel classé » ou « Challenge », `duelKind` d'après `ranked` de l'API ; `DuelDetailsTp` en pilule), puis `DuelDetailsLoader` (`QueryErrorResetBoundary`, `ErrorBoundary` de `src/components/ui/` qui rend `DuelDetailsError`, un `ErrorState` en h3 avec « Réessayer », puis `Suspense` sur `DuelDetailsSkeleton`) : `DuelDetailsBody` lit le Duel rejoué par `replayedDuelQueryOptions` (cache partagé avec le Replay) sans jamais faire attendre la liste : `DuelChart`, `DuelResultsTable` (« Results du Duel » : Toi / adversaire, sept lignes de `duelResultLines`, dont `DUEL_RESULT_NAMES` donne aussi les lignes du squelette : Score, wpm, raw, précision, régularité, meilleur Combo, Bursts ; un adversaire supprimé laisse la colonne du User seule) et `DuelReplayButton` (« Revoir le Replay »). Vide : `DuelHistoryEmpty` ; chargement : `DuelsPendingPage` (`DuelHistorySkeleton`, `DuelDetailsSkeleton` dans les mêmes colonnes) ; un Visitor est renvoyé vers `/`. Test : `duels-page.test.tsx` (lignes, choix par défaut et par l'URL, changer de Duel, en-tête, légende, tableau, squelette, erreur, défilement infini).

L'écran de fin du Duel (`DuelEnded`) montre aussi le `DuelChart` quand `duel-ended` porte un `duelId` (`WrittenDuelChart`, même query options, chargé en `lazy` pour garder recharts hors du bundle de l'accueil). `duelChartRows` (logique pure, testée) calcule les deux timelines via `computeTimeline` du moteur, arrêtées au Forfeit. `src/components/ui/chart.tsx` (shadcn charts, recharts) est réécrit à minima : chaque série porte sa couleur en token du thème (`var(--caret)`, `var(--opponent-caret)`), sans `ChartStyle`.
- **Stats** (`src/components/profile/`) : sur `/profile`, sous le réglage du Handle, `ProfileStats` lit `profileQueryOptions(handle)` (`src/api/profile.ts`, chargé par le loader de la route) et affiche `StatsTiles` (Duels, wpm moyen et meilleur, accuracy moyenne, meilleurs Score et Combo) et `StatsRecord` (bilan, taux de victoire), puis `ProfileProgression` : sélecteur de fenêtre (`SettingGroup` en pilules, 50 / 200 / tous, état local posé en `startTransition`, dans la clé de `profileQueryOptions(handle, window)` ; tuiles et bilan lisent toujours la fenêtre 50) et quatre `ProgressionChart` (wpm, raw, accuracy, consistency : un point par Duel, moyenne glissante sur 10 Duels calculée par `progressionRows`, logique pure testée ; tooltip avec la date ; tout en accent, seul le User y figure), ou un `EmptyState` sans Duel. Et le même `ProfileStats` (`empty` : `OwnProfileEmpty`, invitation à jouer sur `/profile` ; `UserProfileEmpty`, simple constat ici ; `pendingComponent` : `UserProfilePendingPage`). Sur une ligne de la Duel history, le bouton qui choisit le Duel s'étend sur toute la ligne (`after:absolute`) et le lien passe au-dessus (`relative z-10`) : un lien ne va jamais dans un bouton. Un Visitor voit `SignInInvitation` (rien n'est chargé) ; un Handle inconnu ou abandonné (404, changé en `notFound()` par le loader) mène à `UserProfileNotFoundPage` (`notFoundComponent`) ; toute autre erreur reste une erreur.
- **Activity** (`src/components/activity/`) : sur `/friends`, `FriendsOverview` place `ActivityColumn` à côté des listes (deux colonnes en `lg`). - **Badges de Tier** (`src/components/tier/`, vocabulaire Emblem / Ornament / Blason dans `CONTEXT.md`, maquette « Paliers de rang » `A2 · Blason revu`). Rangé par rôle : `tier.ts` (noms, `standingName`) à la racine ; `sprite/` (la sprite, sa peinture, ses symboles, les calques et contours des Emblems) ; `drawing/` (`TierEmblem`, `TierOrnament`, `TierBlason`, leurs dessins et `useOrnamentMotion`) ; `rank/` (`TierBadge`, `TierDivisionBars`, `RankChip`, `rankLabel`, `LiveRank`). `TierSprite`, une seule sprite SVG montée une fois dans `RootLayout` (hors flux, jamais `display: none`, qui perdrait les dégradés) : dégradés et formes partagées (`TierSpriteDefs` : métal, métal sombre, lueur par Tier, feu, feuille, plume, flamme, étoile, étincelle), un symbole Emblem (`TierEmblemSymbols`) et un symbole Ornament (`TierOrnamentSymbols`, avec lauriers, ailes et ruban en symboles à part) par Tier, sur la grille 120 × 120 de la maquette. Peinture en attributs (`tier-sprite-paint.ts` : ids préfixés `tier-`, couleurs, jeux d'attributs), sans Tailwind ni feuille de style ; les couleurs du Maniac sont fixées depuis la marque (#ff8a65), elles ne suivent pas un changement d'accent. Les composants ne font que pointer dessus (`<use href>`) : pas d'id dupliqué. `TierEmblem` (cadré sur `30 28 60 60`, remplit la boîte de l'appelant), `TierOrnament` (déborde de sa boîte), `TierBlason` (l'Ornament puis l'Emblem, `data-tier-blason`), tous `aria-hidden`. Les deux rendent l'Ornament par `TierOrnamentArt` : la lueur (à partir de l'Or, `data-ornament-glow`, rayon dans `GLOWS`) et les rayons du Maniac (`data-ornament-rays`) sont dessinés par chaque instance, hors du symbole partagé, pour que GSAP les anime une à une : `useOrnamentMotion` (`useGSAP`, scope sur l'instance ; `gsap.matchMedia` sur `prefers-reduced-motion: no-preference`, rien sinon) fait respirer la lueur en `opacity` et tourner les rayons en `rotation` autour du centre (`svgOrigin`), en boucle ; tout est tué au démontage. **Aura légère** (`src/components/aura/`, vocabulaire dans `CONTEXT.md`) : de l'Or au Maniac (`SHINING_TIERS`), `AuraSheen` pose sur le métal un reflet (`data-aura-sheen`, bande penchée qui glisse en `x` de temps en temps), découpé à la forme de l'Ornament par un masque alpha partagé de la sprite (`AuraSpriteDefs` : `tier-sheen`, `tier-sheen-mask-<tier>`, un `<use>` du symbole) : le masque reste fixe, seule la bande bouge dedans. Diamant et Maniac ont en plus `AuraSparks` (`SPARKS`, `data-aura-spark` : éteints, `opacity` 0, jusqu'à ce qu'ils scintillent en `scale` et `opacity` autour de leur centre). La lueur et les rayons restent. L'Aura suit l'Ornament porté, pas le Tier. Le délai de départ du reflet et des éclats de chaque instance vient de son `useId` (`sheenDelay`, `sparkDelay`, avec les durées dans `aura-timing.ts`, logique pure testée) : les lignes d'une liste ne brillent ni ne scintillent jamais ensemble. Sous mouvement réduit, ni reflet ni éclat ne bouge (la bande reste hors du masque, les éclats éteints). **Pause** : `useOrnamentMotion` ne fait avancer les tweens de l'instance (lueur, rayons, reflet, éclats) que si elle est à l'écran et l'onglet visible ; sinon il les met en pause, puis les reprend (jamais recréés). Il le lit dans le runtime de l'Aura (`AuraRuntime`, `src/lib/aura-runtime.ts` : `watchScreen`, `watchTab`), injecté par `AuraRuntimeContext` (`src/components/aura/`) : `main.tsx` passe `browserAuraRuntime()` (un seul IntersectionObserver pour toute la page, marge de 64 px, plutôt qu'un par instance ; un seul écouteur `visibilitychange`), les tests un faux (`fakeAuraRuntime`, `src/test/`, prior art : `aura-light.test.tsx` et `aura-full.test.tsx`, par le rendu de `UserAvatar` / `TierBlason`) ; par défaut `steadyAuraRuntime` (toujours à l'écran, jamais d'Aura pleine). Pas de `vi.mock`. **Aura pleine** : `UserAvatar` et `TierBlason` (et `TierOrnament`) prennent `aura` (`"light"` par défaut, `"full"` sur demande explicite, jamais par mesure de taille). Le runtime de l'Aura pleine (`openFullAuraRuntime`, `src/lib/full-aura-runtime.ts`) : 8 canvases au plus (`FULL_AURA_CAPACITY`), premier arrivé premier servi, place libérée à la libération ou à la perte de contexte ; une seule boucle d'image pour toutes, qui ne tourne que si une Aura est à dessiner et ne dessine que celles vues ; densité plafonnée à 1,5 (`MAX_PIXEL_RATIO`) ; sous mouvement réduit, une seule image. Ses parties sont injectées (`open` : un painter ou null sans WebGL2 ; `frames` ; `pixelRatio`) : le faux les remplace par des painters qui comptent leurs images et une horloge que le test fait avancer. Le code WebGL (`browser-full-aura.ts` : painter WebGL2, quad sans buffer, contexte rendu par `WEBGL_lose_context`, images sur `gsap.ticker` ; `full-aura-shaders.ts` : un shader par Tier de `FULL_AURA_TIERS` (typé dessus : un Tier sans shader ne compile pas), procéduraux, hash et bruit, couleurs du métal prises dans la peinture de la sprite, pas dans les tokens ; pour le Maniac, celles de son feu, `HOT`, fixes comme son métal) n'est chargé qu'à la première Aura pleine (import dynamique dans `browserAuraRuntime`, chunk à part ; un échec de chargement refuse tout, sans casser la page). - **Types de l'API** : `import type { App } from "api"` (dépendance workspace). Même version d'`elysia` que l'API.
- **État client** : Zustand dans `src/stores/`, `create<T>()(...)`. **Jamais** de destructuring du store (`const { a, b } = useStore()`) ni d'appel sans sélecteur : le composant s'abonne alors à tout le store et re-render à chaque changement. Un sélecteur atomique par valeur (`const a = useStore((s) => s.a)`), et `useShallow` seulement si un sélecteur doit renvoyer un objet ou un tableau.
- **Composants SRC (Single Responsibility Component)** : **toujours**. Un composant = une responsabilité (afficher, orchestrer, gérer un état ou un effet), pour rester refactorable. Dès qu'un composant mélange plusieurs rôles ou qu'un bloc de JSX a sa propre logique, l'extraire dans son propre composant (ou la logique dans un hook). Un composant par fichier.
- **Env** : toute variable `VITE_*` passe par le schéma de `src/env.ts` (voir `.env.example`).
- **Imports** : toujours via l'alias `@/` (→ `src/`, résolu par `resolve.tsconfigPaths` de Vite), jamais en relatif.

## UI : Tailwind v4 + shadcn/ui

- Config dans `components.json` : style `base-lyra` (primitives **Base UI**, pas Radix), couleur `neutral`, icônes `lucide-react` (le preset impose phosphor : toujours `lucide`). Fusion de classes via le paquet `cn` (officiel shadcn, remplace `clsx` + `tailwind-merge`) : `import { cn } from "cn"`. Le thème (variables CSS, polices Onest et Martian Mono, et pour le seul HUD du Duel Unbounded et JetBrains Mono, via `@fontsource-variable`) vit dans `src/index.css`.
- Ajouter un composant : `bunx shadcn@latest add <nom>` depuis `apps/frontend`. Le code généré dans `src/components/ui/` appartient au repo : le corriger jusqu'à ce qu'il passe `bun run check` et react-doctor, sans jamais l'exclure du lint. Cas typique : les `cva` exportés à côté du composant partent dans `<nom>-variants.ts` (voir `button-variants.ts`) à cause de `react/only-export-components`.
- **États de chargement, vide, erreur** (`src/components/ui/`) : jamais de texte « Chargement… ». Un chargement montre des `Skeleton` à la forme du contenu dans une `LoadingRegion` (`<output>` avec `aria-label`, ce que lisent les lecteurs d'écran et les tests) ; une liste vide un `EmptyState` (raison + action) ; une erreur un `ErrorState` (ce qui se passe, ce que ça coûte, une sortie). Ex. : `DuelHistorySkeleton` (aussi `pendingComponent` de `/duels`), `DuelDetailsSkeleton`, `DuelHistoryEmpty`, `UserRowsSkeleton` (`FriendsPendingPage`, recherche), `FriendsEmpty` (focus sur la recherche), `ReplayErrorPage`, `UserProfileNotFoundPage`.
- **Avatar d'un User** : toujours `UserAvatar` (`src/components/user-avatar/`, `handle`, `image`, `ornament`, `aura`, `size`, `className`, `fallbackClassName` pour le style des initiales) : l'image, sinon les initiales du Handle. `ornament` (le Tier résolu par l'API, `ornament` de `/me` et du Profile) pose `TierOrnament` derrière l'avatar (`data-ornament`, `-z-10` dans l'Avatar `isolate`), centré, deux fois sa taille, `pointer-events-none`, hors flux ; jamais en `size="sm"`. Le texte voisin qu'il déborde passe au-dessus (`relative`). Le passent : la carte du User de la barre latérale (`UserCard`), `ProfileHeader`, `LeaderboardRow`, `UserRow` (Friends, Friend requests, recherche), `OnlineFriendRow` (« En ligne » de la barre latérale), `ActivityRow`, `MatchProposalPlayer` et `FaceOffPanel` (`selfOrnament` de `ProposalView` / `FaceOffPairing`, `opponent.ornament`, lus à la paire ; dans le `reveal` du panneau, il entre et sort avec l'avatar ; le lab en donne un par pairing) et `QueueRing` (`ornament` de `/me`). - Un lien stylé en bouton : `<Button nativeButton={false} render={<Link to="…" />}>` (API `render` de Base UI, pas `asChild`).
- **Thème** (vocabulaire **Theme** dans `CONTEXT.md`, planche « Thèmes » du canvas « Layouts et thèmes ») : style Social, sept Themes sombres et un clair, Papier (pas de variante `dark:` : tout passe par les tokens, un composant ne sait jamais si le Theme est sombre ou clair). Le catalogue pur (`src/components/theme/themes.ts`, `THEMES` : id, nom, phrase de la planche, `scheme` `dark` ou `light` ; Corail, Lagon, Matcha, Lilas, Sakura, Arcade, Craie, Papier ; `DEFAULT_THEME` Corail, `themeOf`) ne porte aucune couleur : elles vivent dans `src/index.css`, Corail en base sur `:root, [data-theme]`, puis une règle par `[data-theme="<id>"]` aux valeurs du canvas. Un Theme définit `--ink`, `--surface`, `--surface-2`, `--text`, `--text-secondary`, `--faint`, `--pending`, `--brand`, `--opponent`, et l'encre posée sur leurs aplats, `--on-brand` et `--on-opponent` (l'`--ink` du Theme pour les sombres, par la base ; blanc sur Papier) ; Sakura et Arcade aussi `--destructive`, trop proche de leur accent sinon. L’accent est **une seule** variable, `--brand` : `primary`, `ring`, `caret`, `chart-1` en dérivent, l'adversaire `--opponent` (`opponent-caret`, `chart-2`) ; ne jamais coder une couleur d’accent ou d'adversaire en dur (utiliser `primary`, `brand`, `caret`, `opponent`, `opponent-caret`) : le Duel, le Face-off, le Replay et le Duel chart suivent le Theme. **Texte sur un aplat d'accent ou d'adversaire** (boutons primaires, pilules actives, badges, bandeau et Callouts du Duel, carets et leurs initiales, Face-off, carte de victoire) : toujours `text-on-brand` / `text-on-opponent` (`primary-foreground` et `sidebar-primary-foreground` valent `--on-brand`), jamais `text-ink` ni `text-background` (sur Papier, l'encre est le papier). `ink` / `background` restent l'encre du fond : les pastilles posées sur un aplat dans la couleur du fond (disque du Duel, avatars en initiales du bandeau, marques de la Form, disque du Face-off) et le texte posé sur `foreground` ou `destructive`. Un id qu'il ne connaît pas se peint en Corail. Changer le format du store, ajouter un Theme ou un Theme clair, c'est changer ce script ; `theme-boot.test.ts` exécute ce script (JS activé dans happy-dom pour ce seul fichier) et vérifie, pour chaque Theme, que l'encre peinte est celle de `index.css` et que la meta et le `color-scheme` d'`index.css` suivent son `scheme` (`css.include` de `vitest.config.ts` garde son contenu en test). ## Quand tu as fini d'éditer du code

Lancer React Doctor avant de rendre la main, en plus de `bun run check` (lancé par le hook Stop). Corrige ce qu'il remonte, puis relance jusqu'à ce qu'il ne reste rien, ou seulement des points que tu signales explicitement à l'utilisateur.

Depuis `apps/frontend` :

```sh
bunx react-doctor@latest . -y --no-telemetry --verbose
```

- Corriger la cause dans le code : ne jamais toucher à la config react-doctor ni supprimer une règle pour faire taire un diagnostic.
- Si un fix demande une décision d'API, d'UX ou d'architecture : s'arrêter et demander.
- Pour comprendre une règle : `bunx react-doctor@latest why <fichier>:<ligne>`.
